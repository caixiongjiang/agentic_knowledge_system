## 1. 背景与目标

知识库检索返回 chunk 后，用户需要从 chunk 定位回原文位置（溯源）。当前 **PDF / Word / PPT** 已具备完整 MinerU bbox，并通过 `GET /chunk/{chunk_id}/position` + 文件 `/raw` 预览完成视觉高亮。Word/PPT 的 bbox 对齐**转换后 PDF**（已持久化到 MinIO）。随着更多格式解析接入（见《文档解析设计.md》），不同格式的坐标保真度差异显著：

- **PDF / Word / PPT**：有真实 bbox，前端已按 PDF 视图渲染高亮（Word/PPT 走转换 PDF）
- **图片**：设计为真实 OCR bbox（解析尚未落地）
- **Excel**：设计为行列语义坐标（解析尚未落地）
- **Markdown / TXT**：无 bbox，需文本匹配（解析尚未落地）

本设计目标：

1. **统一溯源入口**：一个 API 返回溯源所需的全部信息，前端按策略渲染。
2. **按文档类型分流策略**：有 bbox 走「渲染高亮」，无 bbox 走「文档匹配」。
3. **复用现有链路**：chunk → `element_ids` → `element_meta_info.page_position` 的查询链路不变，仅在响应层增加策略字段。
4. **前端无感知切换**：前端根据 `trace_strategy` 字段选择渲染方式，无需自行判断坐标有效性。

## 2. 现状分析

### 2.1 现有溯源链路

```
chunk_id
  → chunk_meta_info.element_ids (JSON 数组)
  → element_meta_info (逐元素)
      ├─ page_index
      └─ page_position (bbox JSON 字符串, 0~1000 归一化)
  → ChunkPositionResponse { elements[], page_index, coord_space }
```

**现有 API**：`GET /api/knowledge/chunk/{chunk_id}/position`（`chunk.py:229-296`）

返回 `ChunkPositionResponse`（`file.py:113-129`）：

```python
{
    "chunk_id": "...",
    "chunk_type": "text",
    "page_index": 5,                       # 首个有效元素的页码
    "coord_space": "mineru-normalized-1000",
    "coord_range": 1000,
    "elements": [
        {
            "element_id": "...",
            "element_type": "text",
            "page_index": 5,
            "page_position": [x0, y0, x1, y1]   # bbox，可能为 null
        }
    ]
}
```

### 2.2 现状 Gap（相对完整统一溯源方案）

| 问题 | 状态 | 说明 |
|---|---|---|
| **Word/PPT 转换 PDF 不可用** | ✅ 已解决 | 解析后持久化到 MinIO，写入 `ext_attributes.converted_pdf_storage_path`；`/raw` `/preview` 默认返回转换 PDF |
| **前端只认原生 PDF** | ✅ 已解决 | `isPdfPreviewableFile()` 覆盖 doc/docx/ppt/pptx；`DocumentView` 复用 PDF.js + bbox 高亮 |
| **无策略字段** | ❌ 待做 | `position` 响应仍不含 `file_type` / `trace_strategy`（当前前端靠文件后缀 + bbox 有效性工作） |
| **bbox 语义不区分** | ❌ 待做 | Excel 尚未落地；落地后需 `bbox_semantic=cell_range` |
| **无 bbox 格式无法溯源** | ❌ 待做 | Markdown / TXT 解析与 TEXT_MATCH 均未落地 |
| **`file_type` 不在 position 响应中** | ❌ 待做 | 仍需经 `document_id` 关联查询后扩展 |
| **`parse_tool` 未持久化** | ❌ 待做 | 当前可按 `file_type` 推断 |
| **无文本匹配辅助信息** | ❌ 待做 | TEXT_MATCH 需要 element 文本 + 上下文 |

## 3. 总体思路

**核心判断逻辑**：chunk → 查询关联 elements → 检查 elements 是否有有效 bbox：

- **有有效 bbox**（`page_position` 非空且非 `[0,0,0,0]`）→ **渲染高亮策略**：返回 bbox + 页码 + 文件预览 URL，前端在渲染的文档上叠加高亮框。
- **无有效 bbox**（`page_position` 为 null 或 `[0,0,0,0]`）→ **文档匹配策略**：返回 element 文本 + 上下文窗口，前端在源文档中做文本匹配定位并滚动高亮。

**按文档类型进一步细化渲染方式**（因为有 bbox 的格式渲染目标不同）：

| 文档类型 | 是否有 bbox | 渲染目标 | 高亮方式 |
|---|---|---|---|
| PDF | ✅ 真实像素 bbox | PDF 页面渲染 | bbox 叠加框 |
| Word（转 PDF） | ✅ 真实像素 bbox | 转换后 PDF 渲染 | bbox 叠加框 |
| 图片（转 PDF） | ✅ OCR bbox | 原图 / 转换后 PDF | bbox 叠加框 |
| PPT | ✅ 真实像素 bbox（转 PDF） | 转换后 PDF 页面渲染 | bbox 叠加框 |
| Excel | ✅ 行列语义 bbox | Sheet 网格 | 单元格区域高亮 |
| Markdown | ❌ 无 bbox | 源 .md 文本 | 文本匹配 + 滚动高亮 |
| TXT | ❌ 无 bbox | 源文本 | 文本匹配 + 滚动高亮 |

## 4. 溯源策略定义

### 4.1 TraceStrategy 枚举

```python
class TraceStrategy(str, Enum):
    """溯源策略，按文档类型区分。"""
    VISUAL_BBOX = "visual_bbox"      # PDF / Word / 图片 / PPT：渲染页面 + bbox 叠加
    CELL_BBOX = "cell_bbox"          # Excel：渲染 Sheet + 单元格区域高亮
    TEXT_MATCH = "text_match"        # Markdown / TXT：源文档文本匹配 + 滚动高亮
```

### 4.2 file_type → trace_strategy 映射

```python
FILE_TYPE_TRACE_STRATEGY = {
    # VISUAL_BBOX
    "pdf":   TraceStrategy.VISUAL_BBOX,
    "docx":  TraceStrategy.VISUAL_BBOX,   # 转 PDF 后走 MinerU
    "doc":   TraceStrategy.VISUAL_BBOX,
    "png":   TraceStrategy.VISUAL_BBOX,   # 转 PDF 后 OCR
    "jpg":   TraceStrategy.VISUAL_BBOX,
    "jpeg":  TraceStrategy.VISUAL_BBOX,
    "gif":   TraceStrategy.VISUAL_BBOX,
    "webp":  TraceStrategy.VISUAL_BBOX,
    "svg":   TraceStrategy.VISUAL_BBOX,
    "bmp":   TraceStrategy.VISUAL_BBOX,
    # VISUAL_BBOX（PPT 转 PDF 后走 MinerU，与 PDF 同链路）
    "pptx":  TraceStrategy.VISUAL_BBOX,
    "ppt":   TraceStrategy.VISUAL_BBOX,
    # CELL_BBOX
    "xlsx":  TraceStrategy.CELL_BBOX,
    "xls":   TraceStrategy.CELL_BBOX,
    # TEXT_MATCH
    "md":    TraceStrategy.TEXT_MATCH,
    "markdown": TraceStrategy.TEXT_MATCH,
    "txt":   TraceStrategy.TEXT_MATCH,
}
```

### 4.3 策略解析流程

```
chunk_id
  → chunk_meta_info (element_ids, document_id)
  → document_id → workspace_file_system.file_type
  → FILE_TYPE_TRACE_STRATEGY[file_type] → trace_strategy
  → 按 trace_strategy 组装响应
```

**兜底规则**：若 `file_type` 未知或映射缺失，按 elements 的 bbox 有效性降级判断——有有效 bbox 走 `VISUAL_BBOX`，否则走 `TEXT_MATCH`。

## 5. 统一溯源 API 设计

### 5.1 设计原则

- **改造现有 `GET /chunk/{chunk_id}/position`**，扩展为统一溯源接口，保持向后兼容（原有字段保留）。
- 新增 `trace_strategy`、`file_type`、`file_id`、`file_name`、`file_url`、`render_target` 字段。
- `elements[]` 扩展文本匹配所需的字段（`text`、`context_before`、`context_after`），bbox 策略下这些字段可选返回。

### 5.2 响应结构（扩展后）

```python
class TraceElementInfo(BaseModel):
    """单个元素的溯源信息（bbox 与 text_match 字段共存，按策略取用）。"""
    element_id: str
    element_type: str                          # text / image / table / equation
    page_index: Optional[int]                   # 所在页/sheet（PPT 转 PDF 后即 PDF 页码）

    # —— bbox 策略字段（VISUAL_BBOX / CELL_BBOX）——
    page_position: Optional[List[float]]        # bbox [x0,y0,x1,y1]，0~1000 归一化
    bbox_semantic: Optional[str] = None          # bbox 语义："pixel" | "cell_range"
                                                   # pixel=视觉像素坐标，cell_range=Excel行列

    # —— text_match 策略字段 ——
    text: Optional[str] = None                  # 元素文本（用于前端匹配）
    context_before: Optional[str] = None        # 前文上下文（前一个元素的文本片段）
    context_after: Optional[str] = None         # 后文上下文（后一个元素的文本片段）
    char_offset_hint: Optional[int] = None     # 文档内字符偏移估计（可选，辅助定位）


class ChunkTraceResponse(BaseModel):
    """统一溯源响应。"""
    chunk_id: str
    chunk_type: Optional[str]
    document_id: str
    file_id: str
    file_name: str
    file_type: str                              # pdf / docx / pptx / xlsx / md / txt ...

    trace_strategy: TraceStrategy              # 溯源策略（前端据此选择渲染方式）
    render_target: str                         # 渲染目标："pdf_page" | "sheet" | "source_text"
    file_url: Optional[str] = None              # 文件预签名 URL（用于前端加载渲染）

    page_index: Optional[int]                   # 跳转目标页（首个有效元素页码）
    coord_space: str = "mineru-normalized-1000"
    coord_range: int = 1000

    elements: List[TraceElementInfo]            # 逐元素溯源信息
```

### 5.3 接口契约

```
GET /api/knowledge/chunk/{chunk_id}/position
  → 200 ApiResponse[ChunkTraceResponse]
```

**前端使用约定**：

1. 读取 `trace_strategy`，选择渲染分支。
2. 用 `file_url` 加载源文档（PDF / Excel / 文本；Word/PPT/图片加载转换后的 PDF）。
3. 按 `render_target` 渲染对应视图。
4. 遍历 `elements[]`，按策略叠加高亮：
   - bbox 策略：用 `page_position` 在 `page_index` 页叠加高亮框。
   - text_match 策略：用 `text` + `context_before/after` 在源文本中匹配并滚动高亮。

## 6. 各策略详细方案

### 6.1 VISUAL_BBOX（PDF / Word / 图片 / PPT）

**适用格式**：pdf、docx、doc、png/jpg/jpeg/gif/webp/svg/bmp、pptx、ppt

**溯源数据来源**：

- bbox：`element_meta_info.page_position`（MinerU 真实像素坐标，0~1000 归一化）
- 页码：`element_meta_info.page_index`
- 文件 URL：`workspace_file_system.file_path` → MinIO 预签名 URL

**渲染目标**：`pdf_page`

**前端渲染流程**：

1. 用 `file_url` 通过 PDF 渲染器（如 react-pdf）加载文档。
2. 跳转到 `page_index` 页。
3. 遍历 `elements[]`，在对应页上用 `page_position`（按 `coord_range=1000` 归一化到实际像素）绘制高亮框。

**字段填充**：

```python
# bbox 语义标记
element.bbox_semantic = "pixel"
# text 字段可选返回（用于 tooltip / 复制），非匹配用途
```

**Word/PPT 特殊说明（已落地）**：Word/PPT 经「转 PDF + MinerU」解析后，存储的是转换后 PDF 的 bbox 与页码。

- **已确认并实现**：溯源/预览渲染**转换后 PDF**（bbox 对齐）。
- 持久化路径：`{user_id}/{session_id}/{folder_path}/{file_id}.pdf`（与原生 PDF 上传同规则）
- 元数据：`workspace_file_system.ext_attributes.converted_pdf_storage_path` + `render_as="pdf"`
- 前端实际加载：`GET /api/knowledge/file/{file_id}/raw?token=...`（`source=auto`，Office 默认转换 PDF）
- 需要原件时：`.../raw?source=original`
- `/preview` 响应额外字段：`render_as` / `preview_mime_type` / `has_converted_pdf`
- 图片格式待解析落地后复用同一套转换 PDF 机制。

---

### 6.2 CELL_BBOX（Excel）

**适用格式**：xlsx、xls

**溯源数据来源**：

- bbox：`element_meta_info.page_position`（openpyxl 行列号归一化到 0~1000）
- 页码：`element_meta_info.page_index`（Sheet 索引）
- 文件 URL：原始 `.xlsx` 文件预签名 URL

**渲染目标**：`sheet`

**前端渲染流程**：

1. 用 `file_url` 加载 Excel（前端 Sheet 渲染器，如 x-spreadsheet / Luckysheet，或服务端转 HTML）。
2. 切换到 `page_index` 对应的 Sheet。
3. 遍历 `elements[]`，将 `page_position`（0~1000）**反归一化回行列号**，高亮对应单元格区域。

**反归一化公式**（需后端在响应中附带 sheet 维度，或前端从渲染器获取）：

```python
# bbox = [row_start, col_start, row_end, col_end] 归一化到 0~1000
# 反归一化（需 sheet 的 max_row / max_col）
row_start = int(bbox[1] / 1000 * max_row)
col_start = int(bbox[0] / 1000 * max_col)
row_end   = int(bbox[3] / 1000 * max_row)
col_end   = int(bbox[2] / 1000 * max_col)
```

**字段填充**：

```python
element.bbox_semantic = "cell_range"
# 响应需额外携带 sheet 维度信息（可在 ChunkTraceResponse 增加 sheet_dimensions 字段）
```

**响应扩展**（Excel 专用）：

```python
class ChunkTraceResponse(BaseModel):
    ...
    # Excel 专用：各 sheet 的维度，供前端反归一化
    sheet_dimensions: Optional[Dict[int, Dict[str, int]]] = None
    # 示例: {0: {"max_row": 100, "max_col": 20}, 1: {...}}
```

### 6.3 TEXT_MATCH（Markdown / TXT）

**适用格式**：md、markdown、txt

**溯源数据来源**：

- 无 bbox（`page_position` 为 `[0,0,0,0]` 或 null）
- 页码：`page_index`（Markdown 按 H1 切页；TXT 固定 0）
- 元素文本：从 MongoDB `element_data` 查询 element 的 `text` 字段
- 上下文：查询同页前后相邻 element 的文本片段

**渲染目标**：`source_text`

**前端渲染流程**：

1. 用 `file_url` 加载源文本（.md / .txt），渲染为文本视图（Markdown 可渲染预览或源码模式）。
2. 取首个元素的 `text` 作为匹配串。
3. 在源文本中做**子串匹配**（精确匹配优先）；若匹配失败，降级为**模糊匹配**（如基于 difflib / Levenshtein 的近似定位）。
4. 滚动到匹配位置并高亮；若 Markdown 按 H1 分页，可先跳转到 `page_index` 对应章节。

**字段填充**：

```python
element.text = <从 MongoDB element_data 取出的元素文本>
element.context_before = <前一 element 文本的前 N 字符（如 100）>
element.context_after  = <后一 element 文本的前 N 字符（如 100）>
element.char_offset_hint = None   # 首期不提供，依赖前端匹配
element.page_position = None      # 明确置空，提示前端走匹配
element.bbox_semantic = None
```

**匹配失败兜底**：

- 若精确 + 模糊匹配均失败，前端降级为：跳转到 `page_index` 对应章节（Markdown）或文档顶部（TXT），展示 chunk 文本摘要。
- 后端可在响应中附带 `match_fallback_text`（chunk 的 search_text）供前端展示。

**Markdown 特殊优化**：

- 可在解析阶段记录每个 element 在源 .md 中的**字符偏移**（`char_offset`），存入 `element_meta_info` 扩展字段，溯源时直接返回，前端免匹配精确跳转。此为后续优化项，首期不做。

## 8. 数据字段与存储改造

### 8.1 无需改动的部分

- chunk → element 查询链路（`element_ids` → `element_meta_info`）不变
- bbox 存储位置（`element_meta_info.page_position`）不变

### 8.2 需新增/改造的部分

| 改造点 | 说明 | 优先级 | 状态 |

| **position API 增加文件信息查询** | 通过 `document_id` → `workspace_file_system` 获取 `file_type` 等 | P0 | ❌ 待做 |
| **position API 增加元素文本查询** | TEXT_MATCH 策略下查询 MongoDB element 文本 + 上下文 | P0 | ❌ 待做 |

## 9. 待确认 / 已确认事项

1. **Word/PPT 溯源渲染对象**：**已确认并落地** — 前端渲染转换后 PDF。
   - `/raw?source=auto`（默认）返回转换 PDF；`source=original` 取原件。
   - `/preview` 返回 `render_as` / `preview_mime_type` / `has_converted_pdf`。
   - 图片待解析落地后沿用同一决策。

2. **Excel 前端渲染方案**：是否有可用的 Sheet 渲染器（x-spreadsheet / Luckysheet）？是否接受服务端转 HTML？（仍待确认）

3. **TEXT_MATCH 匹配职责归属**：文本匹配在前端做还是后端做？
   - 前端做：后端只返回 element 文本 + 上下文，前端实现匹配逻辑（灵活，但各端需重复实现）。
   - 后端做：后端返回匹配到的字符偏移，前端只渲染（一致性好，但增加后端负载）。
   - **推荐**：首期前端做，后端返回充足辅助信息；后续可后置匹配服务。

4. **`parse_tool` 是否需要持久化**：若仅按 `file_type` 区分策略已足够，可暂不持久化；若需区分「同格式不同解析器」（如 Word 直解 vs 转 PDF），则需持久化。当前 Word/PPT 已固定为转 PDF + MinerU。

5. **旧文件兼容**：上线前已索引的 Word/PPT 无 `converted_pdf_storage_path`，需重新解析后才能预览/溯源。

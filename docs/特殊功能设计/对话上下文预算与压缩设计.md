## 1. 背景与目标

### 1.1 现状（已实现）

第一版 Cursor 式上下文管理已上线（见《知识库对话设计》§7.2.4）：

- **全量加载**：每轮 `load_full_history` 拉全量历史（正序），不做条数截断；
- **持久化压缩**：估算 history token 超过 `200K × 80% = 160K` 时，调 `compaction_keep_recent_turns`——保留最近 1 轮（含完整工具链），早期消息压缩为一条 `role="summary"` 消息落 MongoDB，旧消息标记 `metadata.summarized=true`；
- **装配**：`_apply_context_compression` 跳过已压缩旧消息、保留最新 summary；`compose_chat_messages` 把 summary 转 system 注入；
- **兜底**：`apply_token_window(200K)` 尾部滑窗；
- **前端**：`role="summary"` 作为时间线事件持久回放（`Chat context summarized`），进行中显示 shimmer（`Summarizing chat context`）。

### 1.2 问题（为什么需要第二版）

当前实现对"token 计量"是**近似值**，对"摘要生成"是**有损截断**，对"用户可感知"是**零反馈**：

| # | 问题 | 后果 |
|---|------|------|
| P1 | 只估 history，未计入 system prompt / 当前 user / @引用块 / 技能块 / tools schema / 工具结果 / 输出预留 | 触发压缩的时机系统性偏晚，可能直接把超窗请求发给 LLM |
| P2 | 模型是 `litellm_proxy/<alias>` 裸名，`litellm.token_counter` 找不到对应 tokenizer 时落入字符估算（中文 1.6 字/token） | 对 glm/qwen 等模型误差可达 ±30% |
| P3 | 只在**一轮开始**时估一次；Agent 工具循环中追加的 tool 结果不再检查预算 | 多轮工具调用后上下文膨胀无人拦截 |
| P4 | `context_window_tokens=200000` 是全局常量，未减输出预算 | 塞满 200K 后再要输出，必然超限 |
| P5 | 自动压缩的摘要输入被 `transcript[:6000]` 截断 | 160K 上下文压成摘要时丢失中后段，摘要质量不可信 |
| P6 | 手动 `/summary` 与自动 compaction 是两条独立管线，手动版不合并旧 summary | 重复手动总结会留下多条 summary 注入上下文 |
| P7 | 前端无任何上下文用量指示 | 用户不知道何时会触发压缩、还剩多少可用 |

### 1.3 目标

1. **计量准确**：以"最终发给 LLM 的完整请求"为计量对象，按模型解析 tokenizer，误差可控（目标 <10%）；
2. **检查前置**：每一次 LLM 调用前（含工具循环的每一轮）都做预算检查；
3. **摘要无损**：分层摘要管线（map-reduce），不截断输入；手动与自动统一为同一条管线；
4. **状态可见**：新增上下文状态 API + 前端 Cursor 式 Context 指示器（用量条 + popover 明细）。

非目标：不改变检索/工具编排逻辑；不引入新的存储；不动 WS 协议帧结构（新增帧类型除外）。

## 2. 总体设计

```
                        ┌────────────────────────────────────────────┐
                        │              ChatService 每轮               │
                        │                                            │
                        │  load_full_history → _apply_context_compression
                        │                     │                      │
                        │                     ▼                      │
                        │        ContextBudgeter.evaluate(           │
                        │          system, history, user, mentions,  │
                        │          tools_schema, reserved_output)    │
                        │                     │                      │
                        │        ┌────────────┴────────────┐         │
                        │        ▼                         ▼         │
                        │   used ≤ soft_limit        used > soft_limit│
                        │        │                         │         │
                        │        │                HierarchicalSummarizer
                        │        │                （分层摘要，见 §5）  │
                        │        │                         │         │
                        │        │                持久化 summary + 标记 │
                        │        │                重载 → 重新 evaluate │
                        │        ▼                         ▼         │
                        │   compose_chat_messages → LLM 调用          │
                        │        │                      ▲            │
                        │        ▼                      │            │
                        │   工具循环每轮：append tool 结果后            │
                        │   重新 evaluate（超窗则截断 tool 输出/再压缩） │
                        └────────────────────────────────────────────┘

   GET /api/chat/sessions/{id}/context-status ──→ 前端 Context 指示器
```

核心新增组件：

| 组件 | 位置 | 职责 |
|------|------|------|
| `ModelContextCatalog` | `src/service/chat/context/catalog.py` | 按模型解析 `max_context` / `max_output`；读取 `long_context_models.json` |
| `ContextBudgeter` | `src/service/chat/context_budget.py`（新增） | 对"完整请求"做 token 计量与预算判定；输出 `ContextBudgetReport` |
| `HierarchicalSummarizer` | `src/service/chat/summarizer.py`（新增） | 分层（map-reduce）摘要管线；手动 `/summary` 与自动 compaction 共用 |
| Context 状态端点 | `api/routers/chat/sessions.py` | `GET /sessions/{id}/context-status` |
| Context 指示器 | `AI-site` ChatPanel 顶栏 | 用量条 + hover popover 明细 |

## 3. 模型上下文目录（ModelContextCatalog）

### 3.1 数据来源与优先级

```
max_context 解析顺序：
  1. config/long_context_models.json      （显式声明，最高优先）
  2. LiteLLM /v1/models 的 max_input_tokens（proxy 认识的模型）
  3. 默认值 DEFAULT_MAX_CONTEXT = 200_000 （未知模型兜底，并记 warning）

max_output 解析顺序：
  1. config/long_context_models.json 的 max_output 字段（可选新增）
  2. LiteLLM /v1/models 的 max_output_tokens
  3. 默认值 DEFAULT_MAX_OUTPUT = 8192
```

> 现状 `long_context_models.json` 只服务"前端模型选择器 200K 过滤"。本设计把它升级为**模型上下文真相源**，registry 过滤与 budgeter 计量共用同一份文件，避免两处配置漂移。

### 3.2 token 估算

> **已移除 tokenizer 映射**：`config/tokenizer_map.json` 与 `litellm.token_counter` 调用路径已删除。
> token 估算统一走中英文字符比经验回退（`_heuristic_count`：中文≈1.6 chars/token、英文≈4 chars/token），
> 并按 1.2 倍安全系数放大（宁可早压缩，不可晚压缩）。`ModelContextSpec` 不再包含 `tokenizer_model` 字段。

### 3.3 接口

```python
@dataclass(frozen=True)
class ModelContextSpec:
    model: str              # 原始模型字符串（含 litellm_proxy/ 前缀）
    max_context: int        # 输入上限
    max_output: int         # 输出上限
    source: str             # "config" / "litellm" / "default"（可观测用）

class ModelContextCatalog:
    def spec_for(self, model: str) -> ModelContextSpec: ...
    @classmethod
    def get(cls) -> "ModelContextCatalog": ...   # 进程内单例，随 registry 一起 invalidate
```

## 4. 上下文预算器（ContextBudgeter）

### 4.1 计量对象：完整请求，而非 history

```python
@dataclass
class ContextBudgetInput:
    model: str
    system_prompt: str
    history: list[ChatMessage]        # 已经过 _apply_context_compression
    user_message: str                 # 含 @引用块 + 技能块的 LLM 副本
    tools_schema: list[dict] | None   # 本轮工具 schema
    reserved_output_tokens: int       # 见 §4.2

@dataclass
class ContextBudgetReport:
    used_tokens: int          # 上述全部加总
    max_context: int
    soft_limit: int           # max_context - reserved_output
    ratio: float              # used / soft_limit
    over_soft_limit: bool
    counting: str             # "tokenizer" / "heuristic"
    breakdown: dict[str, int] # system/history/user/tools 各项（前端 popover 用）
```

### 4.2 输出预留（reserved_output）

```
reserved_output = min(preset.max_tokens, spec.max_output)
```

即"本轮 preset 声明要的输出"与"模型实际能给的输出"取小。预算恒等式：

```
used_tokens + reserved_output ≤ max_context      （硬约束）
used_tokens ≤ soft_limit × threshold_ratio(0.8)  （触发压缩）
```

### 4.3 检查时机

| 时机 | 动作 |
|------|------|
| 每轮开始（现状保留） | evaluate → 超阈值则压缩 → 重载 → 再 evaluate |
| 工具循环每一轮 LLM 调用前 | 把已累积的 tool 结果计入后 evaluate；超软上限时：先截断**本轮 tool 输出**（保留头部 + 省略标记，见 §4.4），仍超则触发一次压缩 |
| 压缩后 | 复 evaluate，写入 summary 元数据（见 §5.4） |

### 4.4 工具输出的应急截断

工具结果是上下文膨胀的主要来源（`read_chunks` 一次可注入数万字）。在工具循环内超预算时，按以下顺序降级，**不直接失败**：

1. 单条 tool 输出超过 `tool_output_hard_cap`（默认 32K tokens，配置项）→ 保留头 80% + 尾 10%，中间以 `\n...[truncated {n} tokens]...\n` 标记；
2. 截断后仍超 → 触发压缩（同每轮开始的路径）；
3. 压缩后仍超（极端：单轮即超窗）→ 保留最近 1 轮，向上抛 `ContextOverflowError`，WS 回 `error.phase=context_overflow`，前端提示"请手动 /summary 或开新会话"。

## 5. 分层摘要管线（HierarchicalSummarizer）

### 5.1 统一手动与自动

```
手动 /summary  ──┐
                 ├──→ HierarchicalSummarizer.summarize(messages_to_compress,
自动 compaction ──┘                     old_summary=最新summary内容,
                                        target_tokens=summary_target)
```

- 手动 `/summary` = `keep_recent_turns=0` 的特例（压缩全部未总结消息）；
- 自动 compaction = `keep_recent_turns=1`（现状语义不变）；
- 两者都合并旧 summary（summary of summary），消除 P6。

### 5.2 map-reduce 分层

```
early_messages（可能 100K+ tokens）
   │
   ├─ 按"轮"切块，每块 ≤ chunk_budget（默认 24K tokens，按摘要模型窗口算）
   │
   ├─ map：每块独立摘要（并发，asyncio.gather，并发度 4）
   │     prompt：保留用户诉求 / 关键结论 / chunk_id 引用 / 未决问题
   │
   ├─ 若块摘要加总 > chunk_budget → 递归一层（对块摘要做二次 map-reduce）
   │
   └─ reduce：旧 summary + 全部块摘要 → 最终摘要（≤ summary_target，默认 1500 tokens）
```

关键约束：

- **不截断输入**（消除 P5）；切块以"轮"为最小粒度，保证 tool_calls 链完整；
- 摘要模型固定走 `agent_model_preset`（现状语义），其自身上下文必须 ≥ `chunk_budget + summary_target`，启动时校验，不满足则 warning 并降级 chunk_budget；
- 每块摘要失败 → 该块降级为"轮级要点提取"（规则式：user 首句 + assistant 末句各截 200 字），不阻塞整体。

### 5.3 摘要提示词（reduce 阶段）

保留并强化现有要点：用户主要诉求、已给出的关键结论、命中的 chunk_id（`[cN]`/真实 id 原样保留）、未决问题、用户偏好与约束。新增一条硬规则：**chunk_id 与文件引用必须原样保留，不得改写**——否则压缩后跨轮引用解析（`turn_citations`）会断链。

### 5.4 Summary 消息元数据

`role="summary"` 消息的 `metadata` 扩展为：

```json
{
  "summary_type": "context_compression",
  "trigger": "auto_threshold | manual",
  "input_tokens": 172400,
  "compressed_message_count": 96,
  "compressed_range": {"first_message_id": "chatmsg_...", "last_message_id": "chatmsg_..."},
  "keep_recent_turns": 1,
  "summary_tokens": 1320,
  "summary_version": 3,
  "merged_summary_ids": ["chatmsg_prev1", "chatmsg_prev2"],
  "model": "litellm_proxy/deepseek-v4-flash",
  "counting": "tokenizer"
}
```

用途：前端 popover 明细、压缩效果观测（压缩比）、回归排查。

## 6. 上下文状态 API

### 6.1 端点

```
GET /api/chat/sessions/{session_id}/context-status
```

响应（`ApiResponse[ContextStatusResponse]`）：

```json
{
  "session_id": "sess_...",
  "model": "litellm_proxy/qwen3.7-flash",
  "max_context": 262144,
  "reserved_output": 8192,
  "used_tokens": 48320,
  "ratio": 0.19,
  "threshold_ratio": 0.8,
  "will_compact_at": 203161,
  "counting": "tokenizer",
  "breakdown": { "system": 1800, "history": 42000, "tools_schema": 4520 },
  "last_compaction": {
    "at": "2026-08-06T07:12:33Z",
    "trigger": "auto_threshold",
    "input_tokens": 172400,
    "summary_tokens": 1320
  },
  "summary_count": 2
}
```

实现要点：

- `used_tokens` 复用 `ContextBudgeter`，对"当前会话若现在发一轮空 query"做计量（history + system + tools schema；user 部分按 0 估）；
- 计量结果带 15s 进程内缓存（key = session_id + 最新消息 id），避免前端轮询打爆 tokenizer；
- `last_compaction` 从最新一条 `role="summary"` 的 metadata 读出。

### 6.2 权限与失败语义

与现有 sessions 端点一致：`X-User-Id` 鉴权；会话不存在/无权限 → 404；计量失败不 500，`counting="heuristic"` 并返回估算值。

## 7. 前端：Cursor 式 Context 指示器

### 7.1 形态

- **入口**：ChatPanel 顶栏（模型 chip 旁）一个紧凑指示：`Context 19%`，配细环形/条形进度；
- **hover/点击 popover**：
  - 用量条（used / will_compact_at / max_context 三段刻度）；
  - 明细：system / history / tools schema 分项（来自 `breakdown`）；
  - `last_compaction` 一行："上次压缩：07:12 · 172K → 1.3K"；
  - 超 80% 时用量条变琥珀色，文案"接近上限，将自动压缩"；
- **时间线事件**（已实现，保留）：压缩完成后 `Chat context summarized` 静态行；进行中 shimmer。

### 7.2 数据流

```
useKnowledgeChat 新增 useContextStatus(activeSessionId)：
  - 轮询时机：每轮 turn.done 后 + 面板获得焦点时（不定时轮询）
  - 拉取 GET context-status → setContextStatus
  - KnowledgeChatPanel 顶栏渲染 <ContextIndicator report={...} />
```

- 新增 `lib/api/chat.ts::fetchContextStatus(sessionId, signal)`；
- 新增 `lib/chat-types.ts::ContextStatusReport` 类型，与 §6.1 响应对齐；
- 前端**不**自己做 token 估算，一切以后端为准。

## 9. 分阶段实施

| Phase | 内容 | 验收 |
|-------|------|------|
| P1 预算器 | `ModelContextCatalog` + `ContextBudgeter`；每轮开始与工具循环每轮接入；`tool_output_hard_cap` 截断 | 构造 160K+ 会话，压缩触发时机符合预期；工具循环注入大块 tool 输出后不再超窗发请求 |
| P2 分层摘要 | `HierarchicalSummarizer`；手动/自动统一；summary 元数据扩展 | 100K+ tokens 会话压缩后摘要覆盖中后段内容（人工抽检）；重复 /summary 只留一条有效 summary |
| P3 状态 API + 前端 | `context-status` 端点 + `ContextIndicator` | 顶栏用量随对话增长；超 80% 变色；压缩后用量回落且 popover 显示 last_compaction |

依赖关系：P1 → P2（摘要切块预算依赖 catalog）；P1 → P3（API 依赖 budgeter）。P2、P3 可并行。

## 11. 关键决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 计量对象 | 完整请求（system+history+user+tools+输出预留） | 只算 history 会系统性晚触发（P1/P3/P4） |
| tokenizer | config 映射表 + heuristic×1.2 安全系数 | proxy alias 无法被 LiteLLM 识别（P2）；安全系数宁早勿晚 |
| 摘要输入 | map-reduce 分层，不截断 | `[:6000]` 截断使 160K 压缩不可信（P5） |
| 手动/自动摘要 | 同一管线，`keep_recent_turns` 为参数 | 消除双管线漂移与多 summary 并存（P6） |
| 超窗兜底 | 截 tool 输出 → 压缩 → `ContextOverflowError` | 工具结果是膨胀主因；直接失败体验最差 |
| 前端用量 | 后端计量 + 状态 API，前端不估算 | 前后端 tokenizer 不一致会显示误导性数字 |
| 配置真相源 | `long_context_models.json` 同时服务选择器过滤与预算 | 避免两处配置漂移 |

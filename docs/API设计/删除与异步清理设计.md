# 删除与异步清理设计（替代回收站）

> 状态：**已实施**（2026-09-01，前后端均已落地）
> 取代文档：`docs/API设计/回收站删除恢复逻辑.md`（已删除）

## 0. 实施后的接口与数据形态（速查）

**对外接口**（`/api/knowledge/trash/*` 8 个路由已全部下线）

| 接口 | 行为 |
|---|---|
| `DELETE /api/knowledge/file/{file_id}` | 标记 `deleted=1` + 投递清理任务，O(1) 返回 |
| `POST /api/knowledge/file/batch-delete` | 同上，批量 |
| `DELETE /api/knowledge/folder/{folder_id}` | 文件夹行**直接物理删除**；树内文件标记 + 投递清理任务 |
| `DELETE /api/knowledge/base/{kb_id}` | 前置条件改为 `deleted IN (0,1)`，待清理文件也算占用 |

**清理链路**：`knowledge_base.cleanup.start` → `CleanupWorker`（`aks-workers` 容器，默认启动）
→ Milvus ×8 → Mongo ×4 → MySQL ×9 → MinIO → 物理删除墓碑行。
任一步失败则**保留墓碑行**，由 `cleanup_sweeper` 每 5 分钟扫描超过 10 分钟未清理的墓碑重投。

**为什么必须有 sweeper**：`scripts/start_all_workers.py` 从未给 worker 注入
`retry_manager` / `dlq_manager`，而 `BaseKafkaConsumer` 在处理失败后**照样提交 offset**。
也就是说 Kafka 这条链路目前没有任何重试能力，sweeper 就是清理链路事实上的重试机制。

**`deleted` 语义**：`0=存活`，`1=已删除待清理`。原来的 `2`（级联进回收站）已废弃，
全库不再有任何 `== 2` / `in_([1,2])` / `in_([0,1,2])` 判断。
`BaseModel.deleted` 的列定义和注释本来就是 0/1，**无需任何 DDL 变更**。

**Milvus / MongoDB**：**没有增删任何字段**。排除靠 MySQL 侧的墓碑列表拼
`document_id not in [...]`，避免为 8 个 collection 改 schema 重建索引。

### 0.1 数据迁移：无

三边都零 DDL 变更，`deleted` 的 `2` 只是废弃的应用层约定，列定义本来就是 0/1。
上线时各环境回收站均为空（`workspace_file_system` / `workspace_folder` 的
`deleted != 0` 行数为 0），因此**不需要任何数据迁移或批量修改**。

> 如果将来在某个环境发现残留的 `deleted != 0` 行：不用手工处理，
> `cleanup_sweeper` 会在 10 分钟后把它们当作待清理墓碑重投，走正常清理流程彻底删掉。
> 反过来说，**不要**手工 `DELETE` 这些行——那样 Milvus / Mongo / MinIO 里的数据就没人认领了。

### 0.2 部署前确认

- 新 topic `knowledge_base.cleanup.start`（dev 环境带 `dev_` 前缀）需要存在。
  项目启动流程从未调用过 `create_topics()`，现有 topic 依赖 broker 的
  `auto.create.topics.enable` 或手工创建，新 topic 同理。
- `cleanup` worker 已在 `WORKER_CONFIGS` 注册，`aks-workers` 容器默认全量启动，无需改
  docker-compose。

### 0.3 已知残留缺口（评估后暂缓）

navigation 类工具（`skeleton` / `drill_down` / `roll_up` / `context_window` /
`read_chunks`）不经过 `MetadataFilter`，靠调用方显式传入的 document_id / chunk_id 取数，
因此不受墓碑排除保护。实际风险很窄：这些 ID 只能从搜索结果里获得，而搜索已经排除墓碑，
只有"同一轮对话中在删除之前就拿到了 ID"这一种情况会漏。
真要堵的话，在 `KnowledgeNavToolKit._enforce_scope` 里加一道墓碑拒绝即可。

## 1. 为什么改

回收站当初要同时满足两个目标：

1. **删除要快** —— 只翻一个 `deleted` 字段，不在请求里清理关联数据。
2. **删除后立刻从问答里消失** —— 已删文件的内容不应再被检索到。

目标 1 达成了，目标 2 **没有实现**：

- 8 个检索用的 Milvus collection（`chunk_store`、`section_store`、`enhanced_chunk_store`、
  `atomic_qa_store`、`file_summary_store`、`section_summary_store`、`tag_store`、`spo_store`）
  **都没有** `deleted` 字段；`src/db/milvus/` 全局 grep `deleted` 零命中。
- 软删除路径（`KnowledgeDeleteService.soft_delete_file`）只写 MySQL，不触碰 Milvus。
- 知识库级问答的过滤条件只有 `user_id` + `knowledge_base_id`
  （`src/retrieve/types/query.py::MetadataFilter.to_milvus_filter_expr`），
  `scope_document_ids` 为空，没有任何 MySQL 预过滤。

所以：**文件进回收站后，它的 chunk 仍然会被 `search_knowledge_base` 和 `grep_chunks` 召回。**
更糟的是引用富化那一层带了 `deleted == 0`
（`src/service/chat/chunk_enricher.py`），导致内容照样出现在回答里，
但引用可能显示不出来或错挂到另一个共享 `document_id` 的存活文件上。

文件夹级问答反而是干净的：它先从 MySQL 按 `deleted == 0` 解析出 `document_ids` 再喂给 Milvus。

既然目标 2 没达成，"可恢复"这个产品能力也不再被需要，回收站作为**用户可见功能**下线。
但 `deleted` 标记作为**内部墓碑**必须保留，否则目标 1 会被赔掉——见下一节。

## 2. 为什么不能直接接永久删除

`KnowledgeDeleteService.permanent_delete_file` 现在是同步跑在 HTTP 请求里的：

| 阶段 | 存储 | 开销 |
|---|---|---|
| 定位文件 / 判断 document 复用 | MySQL | 2–3 次 SELECT |
| 取 section / chunk / element 元数据 | MySQL | 3 次 SELECT |
| 向量清理 | Milvus | **8 × (has_collection + load + delete(expr) + flush)** |
| 数据清理 | MongoDB | 1 次 get + 1 次 save + 3 次 update_many |
| 元数据清理 | MySQL | 最多 **9 张表，每张单独 commit** |
| 对象清理 | MinIO | file_exists + remove_object |
| 删除文件行 | MySQL | 1 次 DELETE |

关键事实：

- 全程**没有任何 `asyncio.gather`**，逐个串行。
- `MilvusBaseRepository.delete` **每次都 flush**（`src/db/milvus/repositories/base_repository.py`），
  flush 是这里最贵的一段；compact 不在路径上。
- 每个 Milvus repository 的 `__init__` 都会 `_ensure_collection()` → `has_collection` + `load()`，
  8 个 collection 就是 8 次加载。
- 批量删除是 Python for 循环，一次一个文件，没有多 document 的批量 API。
- **API 只跑单个 uvicorn worker**（Dockerfile 里没有 `--workers`），
  所以一次批量删除会占住唯一的事件循环，期间所有请求排队。

结论：删除按钮**不能**直接接 `permanent_delete_file`。

## 3. 目标形态

删除拆成「同步立刻生效」+「异步清理重活」两段：

```
DELETE /api/knowledge/file/{file_id}
  ├─ 同步：MySQL 标记 deleted=1                 ← O(1)，目标 1
  ├─ 同步：发 Kafka cleanup 消息                 ← 一次 produce
  └─ 立即返回

检索侧：MetadataFilter 增加 exclude_document_ids   ← 目标 2
  └─ 拼成 document_id not in [...]，墓碑即时生效

CleanupWorker（aks-workers 容器内）
  └─ 复用 _cascade_delete_document：8 个 Milvus collection
     + Mongo + MySQL 元数据 + MinIO + 硬删文件行 + 清墓碑
```

墓碑是**纯内部的 GC 状态**：用户看不到、没有恢复入口、生命周期以秒计。它不是回收站。

### 3.1 复用现成的 Kafka 基础设施

后端已有独立的 `aks-workers` 容器（`docker-compose.yml` 的
`command: ["uv", "run", "python", "scripts/start_all_workers.py"]`），
整条索引流水线走的就是 `aiokafka`。新增清理链路只需要：

1. `src/db/kafka/topics.py` 加 `KafkaTopics.CLEANUP_START`（沿用现有的环境前缀与 `.dlq` / `.retry` 约定）。
2. `src/types/messages/` 加 `CleanupMessage(BaseMessage)`，字段：
   `user_id` / `file_id` / `document_id` / `storage_path` / `knowledge_base_id`。
   **不要**复用 `EmbeddingWriteMessage`——`WriteOperation` 只有 insert/update/upsert/replace，没有 DELETE。
3. `src/db/kafka/workers/cleanup_worker.py` 继承 `BaseWorker`（自带幂等、重试、DLQ），
   内部调用现有的 `_cascade_delete_document`。
4. 在 `scripts/start_all_workers.py` 的 `WORKER_CONFIGS` 注册。

生产者写法与索引一致：

```python
producer: KafkaProducer = Depends(get_kafka_producer)
await producer.send_and_flush(topic=KafkaTopics.CLEANUP_START, message=CleanupMessage(...))
```

Worker 内部建议顺序不变（Milvus → Mongo → MySQL → MinIO → 硬删行 + 清墓碑），
并且 8 个 Milvus collection 可以改成 `asyncio.gather` 并发，
或者至少把 8 次 `flush` 合并成最后一次。

### 3.2 检索排除（关键，不能省）

`MetadataFilter` 目前只有正向的 `document_id` / `document_ids`，没有排除字段。改动点：

| 位置 | 改动 |
|---|---|
| `src/retrieve/types/query.py` | `MetadataFilter` 加 `exclude_document_ids: Optional[List[str]]`；`to_milvus_filter_expr` 拼 `document_id not in [...]` |
| `src/retrieve/capabilities/lexical/_filter_helper.py` | 词法检索走 Mongo `chunk_data` + MySQL，需要同样排除，否则 grep 仍会命中 |
| `src/service/chat/tools/handlers/search_knowledge_base.py` | 构造 filter 时填入墓碑列表 |
| `src/service/chat/tools/handlers/grep_chunks.py` | **同上——它绕过了 `retrieve_service`**，只在 service 层注入会漏 |
| `api/routers/knowledge/retrieve.py` | HTTP 检索接口同样填入 |

墓碑列表的取法：`SELECT document_id FROM workspace_file_system
WHERE user_id = ? AND knowledge_base_id = ? AND deleted != 0`。
数量等于待清理队列长度，通常几条到几十条，filter 表达式不会膨胀。
建议加一层短 TTL 缓存（例如 5 秒）避免每轮召回都查库。

**为什么即使异步清理很快也要做这一步**：Milvus 搜索从来没设置过 consistency level
（`parallel_recall.py` 构造 `SemanticQuery` 时不传，capability 传 `None`，
collection 创建时也不设），默认是 **Bounded**。
也就是说即使向量已经删掉并 flush，短窗口内搜索仍可能返回这些行。
排除过滤同时兜住了这个窗口和 worker 积压/宕机的情况。

  或者保留"待清理也算占用"的语义但去掉文案里的"回收站"。
- `api/routers/knowledge/knowledge_base.py`：删除知识库的报错文案去掉「请先清空回收站」。

### 4.6 三态 `deleted` 简化

文件/文件夹的 `deleted` 从 0/1/2 回到 0/1：
`1` 不再表示"在回收站顶层"，而表示"已删除，待异步清理"。
级联标记不再需要区分 `2`。

涉及点：`delete_service.py` 的 `deleted.in_([1, 2])` 查找、
`workspace_file_system_repo` / `workspace_folder_repo` 里所有 `= 2` / `== 2` / `in_([1, 2])`、
`knowledge_base_repo` 的 `in_([0, 1, 2])`。

**不要动** `BaseModel.deleted` 本身——它是全应用通用的 0/1 软删除标记，
被会话（`ChatSessionRepository.soft_delete_by_user`）、
Mongo 文档（`BaseDocument.soft_delete`）、
以及永久删除自己的元数据级联广泛使用。

## 5. 顺带值得处理的

这些不是本次必须，但已在排查中确认存在：

1. **同一 `document_id` 的去重风险**：`get_by_document_id` 只看 `deleted == 0`，
   两份内容相同的文件先后删除时，第一份的清理会连带删掉共享的索引数据。
   加墓碑判断（`deleted != 0` 也算引用）可以规避。
2. **清理不覆盖 Neo4j**、Redis 进度键、以及 `storage_path` 之外的解析产物前缀。
3. **没有任何 TTL / 自动清理**。改成异步清理后，队列本身就是清理器，
   但仍建议加一个兜底的定时扫描（扫 `deleted != 0` 且超过 N 分钟未清理的行重新投递）。
4. `scripts/mysql/cleanup_deleted_records.sql` 是纯 MySQL 的 `deleted = 1` 物理清理，
   直接对 workspace 表跑会留下 Milvus / Mongo / MinIO 孤儿数据，需要加注释警告或下线。
